# Roadmap

Backlog of technical and functional enhancements for the Pegelonline MCP server, based on a review of the current implementation in [pegelonline_mcp/](pegelonline_mcp/).

## Technical & code enhancements

| # | Status | Item | Notes |
|---|--------|------|-------|
| 1 | ✅ Done | Reuse a single `httpx.AsyncClient` (module-level or lifespan-managed) instead of opening a new one per call in all 6 tool/resource functions; add an explicit `httpx.Timeout` | Module-level client with a 30s timeout |
| 2 | ✅ Done | Centralize HTTP error handling — catch `httpx.HTTPStatusError` / `RequestError` / `TimeoutException` and return a clear message instead of letting raw exceptions propagate to the MCP client | Raised as `ToolError` in `get_json` (`http_client.py`), with a dedicated hint for 404 (invalid UUID/parameter) |
| 3 | ✅ Done | Extract a shared `_get_json(url, params)` helper — all 6 functions currently duplicate the `async with httpx.AsyncClient() as client: ... raise_for_status() ... .json()` pattern | All tools and resources go through `get_json` (`http_client.py`); the upstream calls are bundled in `client.py` |
| 4 | ✅ Done | Remove unused `List` import from `typing` in `server.py` | |
| 5 | ✅ Done | Guard `search_stations` output size — a broad or empty query can return hundreds of stations and blow up LLM context; add a `limit`/`max_results` param or a summarized response mode | `limit` param (default 50); response reports `total_matches` / `returned` / `truncated`. Stations are compact (`station_summary` plus the `country`/`land`/`kreis`/`einzugsgebiet` fields the filters match on), without alternative names or the aggregated MQTT/link lists: about 24 000 instead of 72 000 characters for 50 Elbe stations |
| 6 | ✅ Done | Fix `states://list` resource — it downloads *every* station via an unfiltered `/search` just to compute distinct `land` values on every single call; add a short in-memory TTL cache (states change essentially never) | In-memory cache with 6h TTL (~600ms → ~1ms on cache hit); empty upstream results are not cached, so a transient empty response is retried on the next read |
| 7 | ✅ Done | Cache `water-bodies://list` too, same reasoning | Same 6h TTL cache |
| 8 | ✅ Done | `get_recent_measurements` pulls the *entire* measurement history for a parameter and slices the last N locally — check whether the official API supports `start`/`end` query params to fetch only the tail server-side | The API supports ISO-8601 periods (`start=PT90M`); the tool now fetches a window of `count` × 2 × the series' interval (`equidistance`, 15 min if unknown; min 1h, max 35 days) and only falls back to the full history if the window has gaps. The fallback requests the full history explicitly (`start=PT50400M`), because without `start` the API returns only the last 10 days |
| 9 | ✅ Done | Make `BASE_URL` / `OFFICIAL_API_URL` overridable via environment variables (current hardcoded values as defaults) | `PEGELONLINE_DICT_API_URL` / `PEGELONLINE_API_URL` |
| 10 | ✅ Done | Add automated tests with `pytest` + `pytest-httpx` (or `respx`) mocking both upstream APIs — currently zero tests exist | `pytest` + `respx`; tool and resource responses checked against `syrupy` JSON snapshots, plus unit tests for geo, mapping, client and cache |
| 11 | ✅ Done | Add `ruff` (lint) and `mypy`/`pyright` (types) as dev dependencies | `ruff` and `mypy` in the dev group, pinned via `uv.lock` and configured in `pyproject.toml` (`uv run ruff check`, `uv run mypy` over the package and the tests); both pass cleanly |
| 12 | ✅ Done | Add a GitHub Actions CI workflow: `uv sync` → ruff → pytest on push/PR | `.github/workflows/ci.yml` on push to `master` and on pull requests: `uv sync --locked` → ruff → mypy → pytest → check that `packaging/requirements.txt` matches `uv.lock` (via `make -C packaging requirements`); actions pinned to fixed versions, read-only token |
| 13 | ✅ Done | Add structured `logging` for outgoing requests/responses to ease debugging tool calls made through Claude | Logs method/URL/params, status and duration to stderr; level via `LOG_LEVEL` (stdio) or `packaging/log-config.yaml` (uvicorn) |
| 14 | ✅ Done | Add a `LICENSE` file — currently missing | [LICENSE](LICENSE) added |
| 15 | ✅ Done | Add server-wide `instructions` to the `FastMCP` server — guide tool selection and value interpretation beyond the per-tool docstrings | Sent on `initialize`; covers coverage limits (federal waterways only), the search → uuid → measurements workflow, coordinate resolution, gauge zero vs. m+NN, unreliable `Q` at low water, raw-data noise |

## Functional enhancements (new tools/resources)

| # | Status | Item | Notes |
|---|--------|------|-------|
| 1 | ✅ Done | `get_station_info` tool — return one station's static metadata (name, agency, coordinates, water body, available parameters) without measurements | Returns uuid, number, names, agency, coordinates, river km, water body and the available parameters (shortname, longname, unit, equidistance, gauge zero) from the official API |
| 2 | ✅ Done | `get_measurement_history` tool — accept `start`/`end` date params for a bounded historical range, not just "last N" | `hours` (default 24) or `start`/`end` with UTC offset, up to 840 hours and 35 days back; the official API keeps a little over 31 days. Values come in rows per hour (per 10 minutes for 1-minute series) with minute-offset columns, plus a summary over all values (count, missing, first/last/min/max, mean). `resolution="auto"` summarizes spans beyond 3360 grid slots per hour; `raw`, `hour` and `day` choose explicitly. 31 days of a 15-minute series take about 30 000 characters; `_meta["anthropic/maxResultSizeChars"]` of 60 000 keeps the largest results in Claude Code's context. `get_recent_measurements` lost `hours` and returns at most 100 values |
| 3 | ✅ Done | `get_characteristic_values` tool — expose the official API's `/stations/{uuid}/{parameter}/characteristicvalues.json` (MNW/MHW/HSW etc.) | Lets the LLM say whether a current reading is high/low/normal — pairs directly with the `state_mnw_mhw`/`state_nsw_hsw` fields `get_latest_measurements` already returns. That path does not exist (404); the tool requests `/stations/{uuid}/{parameter}.json` with `includeCharacteristicValues` and `includeCurrentMeasurement`, so the current value and both states come in the same request. Only W has characteristic values (561 of 737 W series live); they come in the API's order with trimmed long names, `parameter` defaults to `W` |
| 4 | ✅ Done | `find_nearest_stations` tool — nearest stations to a given lat/lon + radius | Queries the dict API with the bounding box around the radius (`bbox_around`), filters precisely by haversine distance and sorts nearest-first (`distance_km` included per station); `radius_km` and `limit` params with truncation metadata like `search_stations` |
| 5 | ✅ Done | `agencies://list` resource | Mirrors `water-bodies://list`/`states://list` for the `agency` search dimension, which is searchable but not browsable today. `states://list`, `agencies://list` and `catchment-areas://list` share one cached unfiltered `/search` (6h TTL) instead of downloading the ~1 MB station list each; 49 agencies live |
| 6 | ✅ Done | `einzugsgebiete://list` resource | Same idea for catchment areas (`einzugsgebiet`) — completes resource coverage of all dict-API search dimensions. Named `catchment-areas://list` to match the other English URIs; 39 catchment areas live, stations without one are skipped. Two names arrive from the dict API with U+FFFD instead of an umlaut (`Fr�nkische Rezat`, `la Moselle Rivi�re`); they are listed unchanged, since the search filter matches them that way |
| 7 | ✅ Done | `compare_stations` tool — fetch the same parameter's latest value across multiple UUIDs in one call | Avoids N round trips for "compare these 3 stations" questions. One request to `stations.json` with `ids`, `timeseries=<parameter>` and `includeCurrentMeasurement`/`includeCharacteristicValues`; the API takes at most 30 ids (HTTP 400 beyond), so `uuids` is capped at 30. The API silently leaves out unknown stations and stations without the parameter and returns its own order: the tool keeps the requested order, drops duplicates, matches uuids case-insensitively and lists the rest in `not_found`. Since W refers to each station's gauge zero, every station also carries its gauge zero, both states and its characteristic values as a compact short name → value map (`{}` for parameters without); `current_measurement` in `mapping.py` is shared with `get_characteristic_values`. 30 Elbe stations take about 13 000 characters |
| 8 | ✅ Done | Human-readable state translation — decode `stateMnwMhw`/`stateNswHsw` numeric codes into plain-language flood/low-water categories in tool output | No translation needed: the API sends the states as strings (`low`/`normal`/`high`/`unknown`/`commented`/`out-dated`), not numeric codes. `get_latest_measurements` reports both separately (`state_mnw_mhw`, `state_nsw_hsw`) and its docstring explains each value; `get_characteristic_values` (#3) returns the reference values behind them (MNW, MHW, HSW and more) with the current value, so a reading can be placed more precisely than the states allow |
| 9 | ✅ Done | `show_stations_map` tool — interactive inline map (MCP App) of all stations within a search radius | Leaflet + OpenStreetMap UI (`pegelonline_mcp/static/stations_map.html`) registered as `ui://pegelonline-dict/stations-map` and linked to the tool via `AppConfig`; renders inline in MCP-Apps-capable clients (radius circle, station markers with popups), other clients get the structured station list |
| 10 | ✅ Done | `show_measurements_chart` tool — interactive chart (MCP App) of a parameter's history, like `show_stations_map` | The model gets only the summary: station, water body, unit, comment, interval, the window as absolute `start`/`end` in UTC and the `get_measurement_history` summary, about 520 characters. The uPlot UI (`pegelonline_mcp/static/measurements_chart.html`, `ui://pegelonline-dict/measurements-chart`) fetches the values of exactly that window through the app-only `get_chart_values` (`AppConfig(visibility=["app"])`; a flat list only in `structuredContent`, about 179 000 characters for 31 days of a 1-minute series; no 35-day check, so a reopened chart shows what the API still keeps) and the characteristic values through `get_characteristic_values`, drawn as switchable lines, at first only those within the curve's range. Texts follow the host locale (German or English). Checked in Claude Desktop on 2026-10-16 with a probe: the UI may call tools, app-only tools stay hidden from the model (also in Claude Code), and the model sees only `content`, not `structuredContent`. The finished chart was tested by hand the same day in Claude Desktop and claude.ai; in claude.ai, too, the UI may call tools and `get_chart_values` stays hidden from the model |
| 11 | ✅ Done | `get_measurements_chart` tool — the official API's line chart of a parameter over a span, as an image for the model | Fetches `measurements.png` for the same windows as #2 (`hours` or `start`/`end`) at a fixed 900 × 400 pixels, about 480 image tokens whatever the span. Returns MCP image content without an output schema. `get_png` in `http_client.py` shares `get_json`'s retries and error handling and rejects anything but `image/png`. A span without values gives an empty chart; #10 shows a chart to the user |
| 12 | ✅ Done | `list_search_values` tool — the valid values of a `search_stations` filter (`land`, `agency`, `einzugsgebiet`, `kreis`, `country`, `gewaesser`), so the model can look them up itself in any client | The list resources (#5, #6, `states://list`, `water-bodies://list`) only reach the model where the client lets it read resources (Claude Code via `ReadMcpResourceTool`) or the user attaches them (Claude Desktop); the server instructions do not mention them. Helps when a substring search finds nothing or too much, e.g. the Mosel catchment named `la Moselle Rivi�re`, or `land=Sachsen` also matching Niedersachsen. Reads the cached station list behind the resources (`all_stations` in `resources.py`) and returns each value with its number of stations, sorted; the resources stay for users. Also covers `parameter`, which matches a whole short or long name rather than a substring (live: `WT` 135 stations, `Wassertemperatur` 20), so the `search_stations` example became `WT`. For `gewaesser` and `parameter` the value is the short name (`NOK`, `WT`) with the long names in `longnames`, since `gewaesser` still matches only short names. Live 22/49/39/165/5/93/21 values for land/agency/einzugsgebiet/kreis/country/gewaesser/parameter, at most about 7 600 characters (`kreis`); the server instructions point to the tool. The Dict API's hidden `/options` endpoint was not used: it mixes in alternative names and has no counts or long names |
| 13 | Open | Forecast series (e.g., `WV`) — check whether they matter | Their values lie in the future. `hours` ends now, so the measurement tools reach them only through `start` with an `end` in the future, which they allow. Live 2026-10-16: 43 stations have `WV` (WASSERSTANDVORHERSAGE; Elbe 19, Oder 8, Rhein 7, Donau 4, Saale 3, two more), but the official API lists it in `timeseries` only with `includeForecastTimeseries=true`, which `fetch_station` does not send, so `get_station_info` does not show it either. `/stations/{uuid}/WV/measurements.json` adds `initialized`, `type` (`forecast` up to about 48 hours, `estimate` beyond) and sometimes percentiles to each value; Kaub has one value every 2 hours for 4 days. St. Pauli has no `WV`, yet its official chart shows a dashed line about a day past now, from a source the JSON does not offer. The values come from the official API; the Dict API loads `stations.json` without that flag and so does not know `WV` (`parameter=WV` → 0), reported as item 6 in `DICT-API-HINWEISE.md` of the Dict API repo |
